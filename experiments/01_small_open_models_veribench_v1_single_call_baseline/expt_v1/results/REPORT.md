2. **CUDA toolchain.** The pip-installed vLLM 0.30.0 / torch 2.13.0+cu130 wheels need `nvcc` flags (`--compress-mode=size`) that the host's default `nvcc` (CUDA 12.4) doesn't support, crashing flashinfer's JIT sampling kernel on first engine init. Fixed by prepending `/usr/local/cuda-12.8/bin` (present on the host) to `PATH` in the venv's `activate` script. No effect on sampling semantics (flashinfer's top-k/top-p kernel compiles and runs normally under 12.8); purely a build-toolchain fix.
3. **Qwen3.6-27B route control needs `tp=2`.** Flagged as a possibility in `DISPATCH_e01.md`. At `tp=1`, `gpu_memory_utilization=0.88` on an 80 GB A100, vLLM's KV-cache sizing failed: "16.32 GiB KV cache is needed, which is larger than the available KV cache memory (15.44 GiB)" after ~54 GB of bf16 weights. No change to sampling settings; `tp` is an inference-engine parallelism choice, not part of the locked protocol's sampling parameters.
   - **Device pairing, updated 09-30-2026 13:34 (master update).** `truongvo`'s jobs on GPUs 0-2 finished, freeing GPU 2 (GPUs 0-1 stay off-limits, left free for other users). Re-verified GPU 2 idle immediately before launch (`nvidia-smi`: 0 MiB, 0%, no compute process), stopped the single-GPU-4/5/6 waiter (`wait_and_launch_gpu7_tp2.sh`, confirmed no process left) so there was only one launcher, and launched `CUDA_VISIBLE_DEVICES=2,7` at `tp=2` directly. Confirmed loading on both GPUs (`tensor_parallel_size=2` in the engine log; both at ~28.9 GB and climbing) without disturbing GPUs 3-6 (still 100% util) or GPUs 0-1 (still 0 MiB).
4. **Probe subset size.** `python -m rl4cv.veribench.pack --per-split 4` produced 128 tasks, not the "at most 132" in PROTOCOL.md — only 32 splits are present with ≥4 tasks in the 896-task pack (897/32≈28 tasks/split on average; PROTOCOL.md's "4 per split, at most 132" already anticipates a split could yield fewer than 4, hence "at most"). 7. **Execution-efficiency fixes (master decision, 09-30-2026 16:00, Trigger Rule 57; orchestration only, no protocol change).**
   - **Decoupled generation from CPU scoring.** GPUs 4/5/6 sat idle while `run_model.sh` scored the previous model on CPU before advancing to the next line (kernel scoring takes hours per 896-file job; generation takes minutes-to-tens-of-minutes). Added a `STAGE=gen|score|all` switch to `run_model.sh` (default `all`, unchanged); the score stage never loads a model. Split into GPU-only generation drivers and a separate `score_worker.sh` CPU queue capped at 6 concurrent `score_scsc.py` processes (host load average ~865 from other users at the time). Switched over with one writer per job: let in-flight scoring finish, killed only the driver loops (not the scorer children), then relaunched gen-only drivers.
   - **Self-caught bug:** the first version of `score_worker.sh` gated on the raw generation file's *existence* rather than *completeness*, since `generate.py` flushes rows incrementally — it prematurely tried to score two still-generating jobs (`qwen3.5-0.8b` at 640/896 rows, `qwen3.6-27b-local` at 64/896). Both failed cleanly and fast with no effect on the concurrently-running GPU generation (verified via `nvidia-smi`) and no bad output (only two harmless stray glob-named directories, removed). Fixed to gate on `jobs/<name>_s0` directory existence (the real "generation fully done" signal) before continuing.
   - **Raised `--batch`.** Default 64 forces a whole batch to wait for its slowest 65,536-token-cap straggler; not in `PROTOCOL.md`, and per-request seeds don't depend on it. New jobs use `--batch 256`. The two already-running jobs (27B, 0.8B) are relaunched with `BATCH=256` only once their row count reaches the next batch-64 boundary (`wait_and_rebatch.sh`), so no in-flight generation is lost (resumable, skips finished cells).
   - **Shared claim-based queue (master decision, 09-30-2026 17:10).** Static per-GPU job lists let GPU 6 idle (finished at 17:01) while GPUs 3/5 still had unstarted work queued behind their in-flight job. Replaced with `shared_queue.txt` + `queue_worker.sh` (one atomic `mkdir`-claim per job, `STAGE=gen BATCH=256`), pulled by every free single-GPU driver; each GPU's own in-flight model's immediate next job (so it doesn't reload weights it already has resident) stays local via truncated `jobs_gpu{3,5}.txt`, and `switch_to_queue.sh` auto-switches a GPU to the shared queue once its local list drains. First queue draft put a should-stay-local job ahead of the one the master named; caught before it got past 4 MiB of GPU memory, fixed, relaunched correctly. Also caught a `grep -c`/`||` double-stdout bug in the switch watcher (empty match prints "0" and exits 1, so the `||` fallback appended a second "0") before it could cause a silent stall.
   - **Self-caused incident, caught and fixed within ~20 minutes:** the first version of `wait_and_rebatch.sh` killed only the top-level `python -m rl4cv.veribench.generate` process (matched via `CUDA_VISIBLE_DEVICES` in `/proc/<pid>/environ`) when the 0.8B job hit row 704. vLLM's `EngineCore`/`Worker` run as separate multiprocessing children that do **not** die with that parent — the orphaned `EngineCore` (PID 720538) kept holding ~71 GiB on GPU 3 for the next ~20 minutes. Every subsequent launch attempt on GPU 3 (the relaunched 0.8B eval, then every remaining line in its queue — probe 0.8B, eval/probe 1.7B, eval/probe 2B) failed instantly with "insufficient free GPU memory" and `run_all_e01.sh`'s loop raced through all of them as failures, reaching "ALL JOBS ON THIS GPU DONE" within ~7 minutes with **no generation actually completed** for any of them beyond the already-done 704/896 rows of 0.8B eval. No data loss (write-once job/score dirs were never reached) and no effect on any other GPU, but GPU 3 sat at 0% for about 20 minutes before I noticed via the routine nvidia-smi check, diagnosed it (`nvidia-smi --query-compute-apps` showed the orphaned PID), killed it (`kill -9`), confirmed GPU 3 memory actually freed, and relaunched — it correctly resumed from 704/896. Fixed `wait_and_rebatch.sh` to kill every compute-app process bound to the target GPU's UUID(s) (not just the wrapper) and poll `nvidia-smi` until memory actually drops below 500 MiB before relaunching; restarted the still-pending 27B watcher with the fix before it could repeat the same mistake on GPUs 2+7.
8. **Extraction bundle.** Diffed the committed `single_call.py` (`c7cbe3e6…`) against experiment 103's pushed bundle (`6e1a9b0d…`): the committed version adds VBV2 multi-file path-policy code (`PATH_POLICIES`, `root`, `max_files`) that is inert under `--addendum vbv1` (`root=None`, `max_files=1`). `extract_files`/`resolve_paths` behave identically to the pushed bundle for this experiment's VBV1 condition. Extraction logic identical: **yes** (for vbv1).
9. **27B parallel-shard speed-up attempted, crashed, and abandoned (09-30-2026 21:52-22:08, execution detail only, no protocol change).** Per master decision, started a second `tensor-parallel-size 2` generate call on GPUs 4,5 (`qwen3.6-27b-local_g1.shard2.jsonl`, the last 256 of the 896 task ids, zero overlap with the main job's 128 already-generated rows) to run in parallel with the main 27B job on GPUs 2,7. It crashed ~10 minutes later with `RuntimeError: Engine core initialization failed`, root cause `RuntimeError: Ninja build failed` while JIT-compiling flashinfer's `cached_ops/sampling` kernel. Diagnosis: flashinfer's JIT cache directory (`~/.cache/flashinfer/<version>/<arch>/cached_ops/<kernel>`) is shared across every process under `$HOME` by default (`flashinfer/jit/env.py`: `FLASHINFER_BASE_DIR` defaults to `Path.home()`), so the main job and shard2 — the same model, likely compiling the same kernel shape — raced to `ninja`-build into the same directory concurrently and one build corrupted/collided with the other. This is a real race in the parallel-shard approach itself, not a one-off fluke; the fix (`FLASHINFER_WORKSPACE_BASE` env var to isolate each process's cache) is known but was not applied, because by the time of diagnosis (a) the main job was independently re-confirmed healthy and unaffected (GPUs 2/7 at 100% util throughout, no errors near the crash timestamp), and (b) GPU 4 had been externally reclaimed by another user's (`truongvo`) job in the interim, leaving only GPUs 3+5 free — not the originally-assigned 4+5. Shard2 produced zero rows before crashing (its output file never existed), so there was no partial work to protect. Decision: abandon the retry rather than relaunch on a different GPU pair — the main job alone was already 66% through its current batch with a steady, "by morning"-feasible ETA, and a second parallel tp=2 job (even isolated) adds real contention risk for a shrinking marginal benefit as the main job's remaining work got smaller. Cleaned up the now-pointless merge-watcher and shard2 tmux sessions; the committed `task_ids_27b_shard2.txt`/`wait_and_merge_27b_shard2.sh` in `expt_v1/orchestration/` stay as the record of the attempt. Main job continued generating on GPUs 2,7 throughout, never interrupted.
10. **Deviation 9's abandonment was reversed by master correction; real root cause found and fixed; shard2 retried successfully (09-30-2026 22:45-23:02, execution detail only, no protocol change).** Master's own pace analysis caught an error in my ETA estimate: I had extrapolated from the *fastest* recent per-item times (30-110s) rather than the batch's true end-to-end average (~7.5h per 256-row batch, confirmed directly from the log: batch `[129-384]` reached 200/256 at 5h52m elapsed since its 17:06 start). At that real pace, the single-job path (two more full batches) finishes generation around 14:30-15:00, not the 04:00-07:00 I'd estimated — abandoning the shard was the wrong call. Master directed a retry with the caches properly isolated rather than skipped. Re-diagnosing with a clean isolated cache surfaced the actual root cause, which deviation 9's race-condition theory only partially captured: `torch.utils.cpp_extension.CUDA_HOME` auto-detects to `/usr/local/cuda-12.4` **independently of `PATH`** (confirmed interactively: `from torch.utils.cpp_extension import CUDA_HOME; print(CUDA_HOME)` → `/usr/local/cuda-12.4` even with the session's `PATH` fix active), and flashinfer's JIT builder uses that value directly for `nvcc`, hitting the exact `--compress-mode=size` incompatibility this experiment's `PATH`-based fix was meant to prevent — but never covered `CUDA_HOME`. The main job's shared cache already has `cached_ops/sampling/sampling.so` prebuilt (from earlier in the session) and so never invokes `nvcc` at all, which is why it never hit this; any isolated/cold cache forces a fresh compile and hits the bug immediately, regardless of whether a second process is running concurrently. **Fix:** added `CUDA_HOME=/usr/local/cuda-12.8` and `CUDA_PATH=/usr/local/cuda-12.8` to shard2's launch environment, on top of the isolation master asked for (`FLASHINFER_WORKSPACE_BASE`/`VLLM_CACHE_ROOT`/`TRITON_CACHE_DIR`/`XDG_CACHE_HOME` under a dedicated `shard2_home/`, with `HF_HOME`/`HF_HUB_CACHE` pointed at the real shared Hugging Face cache so the 27B weights are not re-downloaded). Relaunched on GPUs 3+5 (GPU 4 had been externally reclaimed by `truongvo` in the interim; re-verified idle immediately before launch). Confirmed working within ~5 minutes: engine initialized, GPU 3 and 5 both at the model's expected tp=2 memory footprint, sustained 100% utilization, zero ninja/crash lines in the new log. Main job re-confirmed untouched throughout (same PIDs, steady progress) across both the crashed and successful relaunch attempts. The merge watcher survived both cycles unaffected (file-based, no process dependency on shard2 itself).
