9. **27B parallel-shard speed-up attempted, crashed, and abandoned (09-30-2026 21:52-22:08, execution detail only, no protocol change).** Per master decision, started a second `tensor-parallel-size 2` generate call on GPUs 4,5 (`qwen3.6-27b-local_g1.shard2.jsonl`, the last 256 of the 896 task ids, zero overlap with the main job's 128 already-generated rows) to run in parallel with the main 27B job on GPUs 2,7. It crashed ~10 minutes later with `RuntimeError: Engine core initialization failed`, root cause `RuntimeError: Ninja build failed` while JIT-compiling flashinfer's `cached_ops/sampling` kernel. Diagnosis: flashinfer's JIT cache directory (`~/.cache/flashinfer/<version>/<arch>/cached_ops/<kernel>`) is shared across every process under `$HOME` by default (`flashinfer/jit/env.py`: `FLASHINFER_BASE_DIR` defaults to `Path.home()`), so the main job and shard2 — the same model, likely compiling the same kernel shape — raced to `ninja`-build into the same directory concurrently and one build corrupted/collided with the other. This is a real race in the parallel-shard approach itself, not a one-off fluke; the fix (`FLASHINFER_WORKSPACE_BASE` env var to isolate each process's cache) is known but was not applied, because by the time of diagnosis (a) the main job was independently re-confirmed healthy and unaffected (GPUs 2/7 at 100% util throughout, no errors near the crash timestamp), and (b) GPU 4 had been externally reclaimed by another user's (`truongvo`) job in the interim, leaving only GPUs 3+5 free — not the originally-assigned 4+5. Shard2 produced zero rows before crashing (its output file never existed), so there was no partial work to protect. Decision: abandon the retry rather than relaunch on a different GPU pair — the main job alone was already 66% through its current batch with a steady, "by morning"-feasible ETA, and a second parallel tp=2 job (even isolated) adds real contention risk for a shrinking marginal benefit as the main job's remaining work got smaller. Cleaned up the now-pointless merge-watcher and shard2 tmux sessions; the committed `task_ids_27b_shard2.txt`/`wait_and_merge_27b_shard2.sh` in `expt_v1/orchestration/` stay as the record of the attempt. Main job continued generating on GPUs 2,7 throughout, never interrupted.
10. **Deviation 9's abandonment was reversed by master correction; real root cause found and fixed; shard2 retried successfully (09-30-2026 22:45-23:02, execution detail only, no protocol change).** Master's own pace analysis caught an error in my ETA estimate: I had extrapolated from the *fastest* recent per-item times (30-110s) rather than the batch's true end-to-end average (~7.5h per 256-row batch, confirmed directly from the log: batch `[129-384]` reached 200/256 at 5h52m elapsed since its 17:06 start). At that real pace, the single-job path (two more full batches) finishes generation around 14:30-15:00, not the 04:00-07:00 I'd estimated — abandoning the shard was the wrong call. Master directed a retry with the caches properly isolated rather than skipped. Re-diagnosing with a clean isolated cache surfaced the actual root cause, which deviation 9's race-condition theory only partially captured: `torch.utils.cpp_extension.CUDA_HOME` auto-detects to `/usr/local/cuda-12.4` **independently of `PATH`** (confirmed interactively: `from torch.utils.cpp_extension import CUDA_HOME; print(CUDA_HOME)` → `/usr/local/cuda-12.4` even with the session's `PATH` fix active), and flashinfer's JIT builder uses that value directly for `nvcc`, hitting the exact `--compress-mode=size` incompatibility this experiment's `PATH`-based fix was meant to prevent — but never covered `CUDA_HOME`. The main job's shared cache already has `cached_ops/sampling/sampling.so` prebuilt (from earlier in the session) and so never invokes `nvcc` at all, which is why it never hit this; any isolated/cold cache forces a fresh compile and hits the bug immediately, regardless of whether a second process is running concurrently. **Fix:** added `CUDA_HOME=/usr/local/cuda-12.8` and `CUDA_PATH=/usr/local/cuda-12.8` to shard2's launch environment, on top of the isolation master asked for (`FLASHINFER_WORKSPACE_BASE`/`VLLM_CACHE_ROOT`/`TRITON_CACHE_DIR`/`XDG_CACHE_HOME` under a dedicated `shard2_home/`, with `HF_HOME`/`HF_HUB_CACHE` pointed at the real shared Hugging Face cache so the 27B weights are not re-downloaded). Relaunched on GPUs 3+5 (GPU 4 had been externally reclaimed by `truongvo` in the interim; re-verified idle immediately before launch). Confirmed working within ~5 minutes: engine initialized, GPU 3 and 5 both at the model's expected tp=2 memory footprint, sustained 100% utilization, zero ninja/crash lines in the new log. Main job re-confirmed untouched throughout (same PIDs, steady progress) across both the crashed and successful relaunch attempts. The merge watcher survived both cycles unaffected (file-based, no process dependency on shard2 itself).
