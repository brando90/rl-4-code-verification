**Retry, this cycle (Trigger Rule 57, orchestration only) — found the real root cause and fixed it:**
- The original diagnosis (shared-cache race between the main job and shard2 both JIT-building into `~/.cache/flashinfer`) was incomplete. The actual trigger, found by rebuilding with an isolated-but-empty cache and reading the full `ninja` invocation line in `$WORK/run_27b_shard2.log`: the compile command used `/usr/local/cuda-12.4/bin/nvcc` explicitly — **not** the `/usr/local/cuda-12.8/bin` from `PATH`. `torch.utils.cpp_extension.CUDA_HOME` auto-detects independently of `PATH` and resolved to `/usr/local/cuda-12.4` regardless (confirmed interactively: `python -c "from torch.utils.cpp_extension import CUDA_HOME; print(CUDA_HOME)"` → `/usr/local/cuda-12.4`, even with the `PATH` fix active). flashinfer's JIT build uses that `CUDA_HOME` value directly, hitting the exact `--compress-mode=size` incompatibility this experiment already fixed once for `PATH`-based resolution, but never for `CUDA_HOME`. The main job never hit this because its shared cache already has `cached_ops/sampling/sampling.so` **prebuilt** from earlier in the session — it never needs to invoke `nvcc` at all. Shard2's first attempt (both the original shared-cache one and my first isolated retry) crashed because an **isolated/cold cache has nothing prebuilt**, forcing a fresh compile that then hit the broken `CUDA_HOME` default.
- **Fix:** relaunched a third time with `CUDA_HOME=/usr/local/cuda-12.8` and `CUDA_PATH=/usr/local/cuda-12.8` added explicitly (on top of the `PATH` fix, which alone isn't sufficient), keeping the isolation master asked for: `FLASHINFER_WORKSPACE_BASE`, `VLLM_CACHE_ROOT`, `TRITON_CACHE_DIR`, `XDG_CACHE_HOME` all point at a dedicated `$WORK/shard2_home/`, while `HF_HOME`/`HF_HUB_CACHE` point at the real shared Hugging Face cache (`/lfs/skampere1/0/brando9/.cache/huggingface`, confirmed to already hold the full 27B weights — no re-download).
