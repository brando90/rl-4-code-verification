# Persistent host selection and execution

**Doc link:** [experiment home](README.md)

**TLDR:** Both complete execution paths are prepared and the ordinary-code watchers are armed. Six disposable Linux CPU routing controls passed. No full 1.7B GPU control or production update is claimed while the authenticated SNAP connection and checkpoint transfer are missing.

## Single production condition

The actual second condition uses V18's final accepted original pool, with all 2,585 original identities explicitly admitted or excluded, plus the unchanged 8,355 previously admitted non-original rows. The 818-replacement V13 snapshot is used only for a discarded hardware control. `prepare_final_transfer.py` binds V18 completion, accepted rows, replacements, all-row accounting, the protected screen and every exact portable proof receipt. `assemble_final_data.py` verifies those bytes, frozen sources, initial weights, immutable prompts, current kernel reports and FILE/token limits before freezing the final schedule. No already verified training proof is recompiled by the assembler.

## Cross-host GPU phases

The local ordinary-code `coordinate_gpu_phase.py` owner grants at most one V19 GPU phase at a time. If SNAP's final CPU preparation becomes ready first, it grants the SNAP selector and fences pending GX control if SNAP is chosen. If GX's initial inputs become ready first, it grants the disposable GX control and waits for its actual full-model and sampling-control completion before granting the SNAP selector. A healthy V17 job is preserved; V17 plus one V19 GPU phase remains at most two fresh jobs.

The SNAP selector checks the E08 and E13 admission locks, live leases, device locks, GPU contexts and memory use. It considers devices 1, 2, 0 in that order and requires a truly empty unleased device with at least 79,000 MiB. It writes one immutable `production_host.json` before production updates. If an adequate SNAP device is unavailable, GX10 is selected. No foreign process is stopped and no idle GPU is allocated while waiting for data or cross-host permission.

## Complete paths

- SNAP: `arm_final_selector.py` waits only for an existing authenticated SSH master, copies hash-checked source and starts remote `watch_selector.py`. Its `select_and_run.py` performs final CPU assembly, host selection, discarded full-model control, fresh-initialization training, original vLLM generation of all 1,080 fixed cells, pinned CPU scoring and the original binary analysis.
- GX10: `watch_chain.py` owns `chain_gx10.py`. It waits for exact initial/evaluation/final transfer receipts and Astra wrapper SHA readiness. After the discarded full-model control and per-cell sampler controls, it assembles the final cohort, verifies the single host decision, reloads initial weights with a fresh optimizer, trains, generates all 1,080 fixed cells with the explicitly recorded GPU Transformers backend and applies the pinned native scorer and original binary analysis.
- Artifact relay and the Astra training wrapper remain separate single-writer responsibilities. After all inputs and grants are staged, GPU training, generation and scoring run remotely without the Mac or an active chat. Cross-host input relay and the initial host/phase handoff still require the Mac's authenticated connections.

The GX inference dtype is prospectively recorded as float16, batch 16. This is an explicit backend/runtime change from the original SNAP vLLM route; numerical equivalence is not claimed. All frozen prompts, per-cell seeds, sampling settings, declarations, extraction and binary-success rules remain checked. The test split remains sealed.

## Death and failure records

The watches record owner/child identities, progress, terminal failures and bounded owner recovery. Completed child results are reconciled after owner death. Healthy child processes are monitored and are never killed merely for stale progress. The Linux CPU control covers missing-completion waiting, nonzero child failure, interrupted-optimizer preservation, completed-child reconciliation and both GPU phase orders; its exact parsed-source hashes are in `results/pipeline_cpu_controls.json`.

An interrupted optimizer trajectory after its first update is preserved and explicitly reported for checkpoint recovery; it is never silently reset to create a new run. Full and partial checkpoints, raw generations, compiler logs and model weights remain on the execution host. Compact all 1,080-cell and 135-task result tables and the final summary are generated for publication.
