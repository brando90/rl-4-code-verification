# Heuristics for RL experiments (rules learned; append new ones at the end)

**Doc link:** <https://github.com/brando90/rl-4-code-verification/blob/main/docs/HEURISTICS.md>

**TLDR:** Short rules that stop avoidable mistakes in RL runs. Each rule says where it came from. Brando asked for this file on 10-28-2026 (voice, 13:04): verify what RL practitioners do, reuse Varun's RL setup as much as possible, and add new rules here as they are learned. `CLAUDE.md` and `AGENTS.md` link to it.

## Rules

1. **bf16 is the community default; any other precision needs a measured reason on the target GPU.** NeMo RL v0.6.0 ships `precision: "bfloat16"` and verl's rollout dtype is bfloat16 ([NeMo RL config](https://raw.githubusercontent.com/NVIDIA-NeMo/RL/v0.6.0/examples/configs/grpo_math_1B.yaml), [verl rollout.yaml](https://raw.githubusercontent.com/volcengine/verl/main/verl/trainer/config/rollout/rollout.yaml)). Start from bf16 plus a rollout-correction (token-level truncated importance sampling with cap 2 to 5, or sequence-level masking: [verl rollout_corr](https://verl.readthedocs.io/en/latest/algo/rollout_corr.html), [MiniMax-M1](https://arxiv.org/abs/2506.13585), [ScaleRL](https://arxiv.org/abs/2510.13786)). Before the first real run on a GPU type, measure the vLLM-versus-trainer log-probability mismatch for the exact model in each dtype (Experiments 21 and 22 harness) and record it.
2. **When bf16 fails the mismatch gate, fp16 is the measured fallback, not a hardware preference.** For Qwen3-1.7B SFT bf16/bf16 gave 6.1% (A100) and 6.4% (A4000) mismatched tokens against a 1% gate, fp16/fp16 0.109% (A100) (Experiments 21 to 24). fp16 needs fp32 master weights and loss scaling (static 16384 in Experiment 24). One lab argues fp16 is generally better for RL ([Qi et al., arXiv 2510.26788](https://arxiv.org/abs/2510.26788)); another argues the mismatch is an optimisation issue ([arXiv 2602.01826](https://arxiv.org/abs/2602.01826)). Record the dtype and why in every protocol. Do not change a frozen gate to make bf16 pass without Brando's word.
3. **Reuse Varun's RL setup before building our own.** His verl Pilot 1 recipe (Qwen3-1.7B: G=8, lr 1e-6, clip 0.2/0.28, KL 0, T 0.6, top-p 0.95, top-k 20, vLLM memory 0.45, bf16, FlashAttention-2 with remove-padding) and his NeMo RL paper runs (bf16, lr 2e-6, importance correction on). Adapt only what the hardware forces (for example, B200-only Triton kernels, sm_100 wheels and FP8 do not exist on Ampere A4000/A100). His NeMo YAMLs are not in any repository we can read (they are in the paper's supplementary archive); ask Varun for them before claiming what his precision or correction settings were.
4. **Name the VeriBench release and the git pins in every protocol** (D-110, `CLAUDE.md`).
5. **One solid experiment beats many weak ones** (Brando, 10-26-2026): on the mercury machines taking 5 to 8 GPUs, or the whole node, for one sanity-checked run is fine. Release idle GPUs when a stage ends.
6. **No branches** (Brando, 10-28-2026): experiments go straight to `main`, each in its own numbered folder.
